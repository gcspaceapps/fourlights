# pipeline/: the precompute

**What lives here:** Python (venv, pinned dependencies in `pyproject.toml`), package `src/four_lights/`, tests in `tests/`, and a `Makefile`. It fetches raw NASA files into `../data/raw/`, computes horizon profiles and Sun/Earth ephemerides, and writes the published JSON into `../web/public/data/`.

**Entry points:** `make venv`, `make test`, `make lint`. Data: `make fetch` (raw files, SHA-256 checked), `make horizon` (one site's horizons → `data/derived/horizons/<id>.json` and a skyline plot in `stages/02_build/output/media/`), `make bruteforce` and `make grass` (the independent checks). `SITE=` and `PGDA=` pick the site (default Shackleton rim / Site04). Code: `geometry.py` (projection, ENU frame), `dem.py` (GeoTIFF and PDS readers), `horizon.py` (the engine), `sites.py` (site point rule), `sources.py` (URLs and SHA-256s). `ephem.py` / `run_ephem.py` (JPL Horizons, SPICE fallback and check), `regions.py` (USGS Artemis region centres), `publish.py` (merge into the data contract), `run_sites.py` (all 12), `dsn.py` (Canberra Link: DSN station visibility), `scenario.py` (the app's rules in Python: threshold check and demo-scenario scan), `validate.py` / `validate_spread.py` (Barker 2021 comparison), `site_review.py` (AI-written site reviews on Workers AI through the `cf` CLI, with the number and wording checks), `qgis_layers.py`, `sites_table.py`. More targets: `make ephem`, `make publish`, `make sites` (everything, all 12 sites), `make validate` (Barker 2021 comparison), `make qgis` (check layers), `make map` (the web map's hillshade), `make regions`; `python -m four_lights.scenario` (demo-scenario scan), `python -m four_lights.sites_table` (regenerates the table in `_shared/sites.md`), `python -m four_lights.fetch --all --refresh` (re-download everything from the original URLs).

**The QGIS pack:** `make qgis-pack` runs `qgis-pack.sh`: the app's layers as files QGIS reads straight from the site (two Cloud Optimized GeoTIFFs, eight FlatGeobuf layers, the same vectors as one GeoPackage) and `four-lights.qgs`, the project that opens them, all into `../web/public/qgis/` (about 7 MB, committed, deployed with the site). It needs `make sites`, `make map` and `make qgis` already run here, GDAL's command-line tools (built with 3.12.2) and QGIS with its Python at `/usr/share/qgis/python` (built with 4.2.3). `src/four_lights/qgis_pack.py` writes the four planner layers from the app's own numbers (venv Python, tested in `tests/test_qgis_pack.py`); `src/four_lights/qgis_project.py` builds and checks the project and needs QGIS's Python, so the script runs it with the system `python3`, not the venv. The demo dates live in `qgis_pack.py` (`PLANNED`, `SLIP_DAYS`). **The site's address is written into the project file** (`QGIS_URL`, default `https://fourlights.gcsa.space/qgis`): if the address changes, rebuild. To check a build: `make qgis-pack QGIS_URL=http://127.0.0.1:8797/qgis`, serve the site there, `make qgis-verify`, then rebuild for the live address before committing. Three 20 m rasters (30 to 65 MB each, from `LDEM_875S_20M`) are too big to be static files: the script builds them once into `../data/derived/qgis-pack/r2/` and they are uploaded by hand to the R2 bucket bound in `../wrangler.jsonc`, only when they change: `wrangler r2 object put q7m3-qgis-poc/<file> --file ../data/derived/qgis-pack/r2/<file> --content-type image/tiff --remote` (with `CLOUDFLARE_ACCOUNT_ID` set; `--local` loads them into `wrangler dev`'s bucket instead). Rebuild the pack after any run that changes `planner.json` or a horizon.

**In a container:** `../ops/data-docker` takes the same arguments as `../ops/data` and runs them in the image built from `Dockerfile` (build context: the repo root; `../.dockerignore` keeps it small), so a machine needs only Docker or Podman: no uv, Python or Node. The image is Node 26 on Debian with uv, Python 3.14 and the pinned packages (about 1 GB); rasterio's wheel carries its own GDAL. Mounted in: `data/` (NASA's files and the intermediate results; `FOURLIGHTS_DATA` puts it elsewhere), `web/public/data/`, `sites.extra.json`, the data manifest and the skyline plots, so a run leaves the checkout as `ops/data` does. Checked Sun 15 Nov: Shackleton rim built in the container in 78 s gives the published site file exactly, bar its `built_utc`, and the same `planner.json`. The QGIS pack and the site reviews are not in the image (they need QGIS, GDAL's command-line tools and the `cf` CLI).

**Where it runs: three ways, one set of code.** All three run the same modules and give the same files.
1. **On our own machines: `../ops/data`.** How the 12 curated sites are built, and the fallback for everything else: it needs nothing but this repo, `uv`, Node and NASA's files, so it works with no container, no hosted machine and no account anywhere. If the hosted run below is ever down or switched off, add the site here (`../ops/data add ...`), commit and deploy, exactly as before.
2. **In a container: `../ops/data-docker`** ("In a container" above), for a machine with only Docker or Podman.
3. **On a hosted machine, for a site someone adds to a shared project** (Sun 15 Nov): the app's Worker starts a Fly.io Machine from the same image, the machine runs `../ops/site-job` (which is `ops/data add ...` followed by `python -m four_lights.deliver`), and the finished site file is sent back to the Worker, which stores it for that project. The Worker side is `../api/src/pipeline.ts`; the routes, the settings that switch it on and its limits are in `../api/CONTEXT.md`, "Computing a project's site".

**The hosted machine (Fly.io):** Steve's Fly account has one app for the pipeline and a 10 GB volume in `syd`, mounted at `/app/data` so NASA's files are downloaded once. Their names are not written in this repo: `fly apps list` and `fly volumes list --app <app>` show them to whoever is signed in. The volume mounts on one machine at a time, so one site is computed at a time; a second request is told to try again in a few minutes. The volume is billed while it exists; a run is about a minute and a half of a 2-CPU, 4 GB machine, which destroys itself afterwards.
- Publish a new image after the pipeline changes: `fly deploy --app <app> --dockerfile pipeline/Dockerfile --build-only --push --image-label <label>` from the repo root, then give the Worker its address (`FLY_IMAGE`, see `../api/CONTEXT.md`).
- Run any `ops/data` command there by hand: `fly machine run . --dockerfile pipeline/Dockerfile --app <app> --region syd --vm-cpus 2 --vm-memory 4096 --volume <volume>:/app/data --restart no --detach -- <the arguments ./ops/data takes>`, then `fly logs --app <app>`. A hand-run machine's published files are gone when it stops unless the command copies them to the volume.
- Try the whole loop without Fly: run the Worker locally with the `FLY_*` values set and `FLY_API_BASE` pointing at anything that answers 200, ask for a site, then run the image yourself with the `RESULT_URL` and `RESULT_TOKEN` the Worker sent (`podman run --network host -e RESULT_URL=... -e RESULT_TOKEN=... --entrypoint ./ops/site-job fourlights-pipeline <id> "<Name>" <lat> <lon_e>`). Checked this way on Sun 15 Nov: a new point near Connecting Ridge was computed in 85 s, stored, and drawn by the page.

**Adding a site:** `./ops/data add <id> "<Name>" <lat> <lon_e>` at the repo root (or `python -m four_lights.add_site ...` then `python -m four_lights.run_sites <id>`). Added sites live in `sites.extra.json` and are loaded into `SITES` by `sites.py`; the site is the given point, snapped to its pixel in the finest DEM that covers it, and gets the same horizons, ephemerides, station bits and validation files as the curated 12.

**Run / test:** needs `uv` and `ruff`, and `NASA_CACHE` pointing at the offline mirror (fallback only). `npm run check` at the root also runs ruff here. Read big DEMs in windows: the machines have 4 cores and 14 GB.

**After any run that changes a site file:** `npm run planner-data` at the repo root (refreshes `web/public/data/planner.json`; `npm run check` fails until it is done), and `python -m four_lights.site_review` if the figures moved.

**Rules:** the technical traps in `../stages/01_data/CONTEXT.md` (true north at the pole, scaled PDS integers, sector maximum, finest covering DEM). Every run logged in `../stages/01_data/output/data-manifest.md`. No hand-edited outputs.

**Touches:** `_datasets/` cards for LOLA, Horizons, SPICE and USGS (fill in their loading recipes); the data contract in `../_shared/stack.md` and `web/src/types.ts`.
