# web/: the front end

**What lives here:** Vite + TypeScript (no framework), `index.html`, and in `src/`: `main.ts` (page wiring, URL-hash state, theme switch), `lights.ts` (the four lights, usable days, every threshold), `chart.ts` (Sun-Path Chart, SVG), `planner.ts` (Slip Planner), `pointing.ts` (the raw azimuth/elevation/terrain/clearance table and the hourly CSV export), `battery.ts` (Survive the Night: presets, simulation, strip chart), `icons.ts` (Phosphor icons for the four lights, and the info tips: add `data-info="..."` to any element in `index.html`, or call `infoTip()`), `tabs.ts` (each `[data-tab]` panel in `index.html` is a tab; Learn-only panels are Learn-view tabs; ←/→ step through them, the tab is `tab=` in the URL hash), `segmented.ts` (turns a short `<select>` into a button group; the hidden select stays the source of truth, so set its value and dispatch `change`, never the buttons), `shortcuts.ts` (keyboard shortcuts and the Ctrl+/ help dialog; the `SHORTCUTS` list in `main.ts` drives both), `map.ts` (the Map tab's page wiring: layer switcher, graticule toggle, legend, the site list that is also the keyboard path; it loads `globe/` only when the tab is first shown and destroys it when you leave), `globe/` (the 3D Moon in three.js, pinned `three` 0.187.0: `math.ts` is pure maths with unit tests, `tiles.ts` the Moon Trek tile quadtree, `globe.ts` the scene, controls, markers and graticule; the polar hillshade `public/map/south-pole-hillshade.jpg`, made by `make map` in `pipeline/`, is draped on a spherical cap), `summary.ts` (the planner's precomputed figures: `scripts/build-planner-summary.mjs` runs it in Node to write `public/data/planner.json`, and the planner reads that file; keep its imports with explicit `.ts` extensions), `data.ts` (lazy JSON loading, including `public/data/reviews.json`, the AI-written site reviews), `types.ts` (data contract), `style.css` (design tokens, dark and light). Plus `public/data/`, the published JSON from the pipeline, served at `/data/...`. Builds to `web/dist`, which the Worker serves.

**Entry points:** `index.html` → `src/main.ts`. Data types: `src/types.ts` (written in S1 from the data contract in `../_shared/stack.md`).

**Run / test:** `npm run dev` at the repo root (build + `wrangler dev`), or `npm run dev -w web` for Vite alone. `npm run check` before every commit. `npm run check:real-data` (part of `npm run deploy`) fails if any `fake-` fixture is in `public/data/`; `npm run fake-data` regenerates the three fixtures for UI work, never to be committed.

**Third page:** `how.html` (served at `/how`, entry `src/how.ts`): the solutions-architecture page, with Mermaid diagrams (the `mermaid` package loads only there). Keep its numbers (test counts, sizes) in step with reality. `learn.ts` draws the Learn view's two data charts from the loaded site file.

**Second page:** `sources.html` (served at `/sources`, entry `src/sources.ts`): the data-sources page, written from the `_datasets/` cards. When a card changes, change this page too. Both pages are listed in `vite.config.ts`.

**Views:** `data-view` on `<html>` is `mission`, `explore` or `learn` (switch in the header, `V` key, `v=` in the URL, remembered per browser). Mark content with class `v-explore` (hidden in Mission), `v-learn` (Learn only) or `v-mission` (Mission only); the rules are in `style.css`. Teaching text lives in `index.html` and must stay factual and sourced from the same data.

**Tests:** unit tests in `tests/` and `../api/tests/` (`npm test`, part of `npm run check`): `lights.test.ts` (the rules on known answers and on the real files), `globe.test.ts` (the globe's maths), `dom.test.ts` (chart, battery strip, icons, button groups and shortcuts against a simulated DOM), `../api/tests/worker.test.ts` (the Worker with stubbed bindings: password gate, `/api/ask`). They cover the light rules, the disc, the battery, the planner sentence and summary, the AI-reply validator, and the demo scenario on the real files. Coverage: `npm run coverage` (table in the terminal, HTML in `../coverage/web/` and `../coverage/pipeline/`). End-to-end tests in `../e2e/` (`npm run test:e2e`, Playwright with the installed Chrome, about 30 s, **not** part of check): the demo scenario through the UI, the chart, views, theme, shortcuts, map, the question box with the model stubbed, the API, and the password gate on a second local Worker. Run them before a deploy that changes behaviour. To watch them in a browser: `npm run test:e2e:watch` (visible Chrome, slowed down) or `npm run test:e2e:ui` (Playwright's interactive window).

**Rules:** the four lights, mission window and usable days follow `../_shared/concept.md` exactly; thresholds are named constants in one file. The browser does the maths (the Worker can't: 10 ms CPU). Its own clean design (Space Apps colours not required, see `../_shared/brand.md`), 4.5:1 contrast, keyboard-usable. Phones are a design goal, not a priority: nothing should break, wide views scroll sideways. Each NASA dataset is named on screen, and anything that is our own definition or an illustrative number says so in its info tip.

**Touches:** `public/data/` is written by `pipeline/` (see `../_datasets/`). If you change the data shape, change `../_shared/stack.md`, `src/types.ts` and the pipeline together.
