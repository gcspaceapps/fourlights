# web/: the front end

**What lives here:** Vite + TypeScript (no framework), `index.html`, and in `src/`: `main.ts` (page wiring, URL-hash state, theme switch), `lights.ts` (the four lights, usable days, every threshold), `chart.ts` (Sun-Path Chart, SVG), `planner.ts` (Slip Planner), `pointing.ts` (the raw azimuth/elevation/terrain/clearance table and the hourly CSV export), `battery.ts` (Survive the Night: presets, simulation, strip chart), `icons.ts` (Phosphor icons for the four lights, and the info tips: add `data-info="..."` to any element in `index.html`, or call `infoTip()`), `tabs.ts` (each `[data-tab]` panel in `index.html` is a tab; Learn-only panels are Learn-view tabs; ←/→ step through them, the tab is `tab=` in the URL hash), `segmented.ts` (turns a short `<select>` into a button group; the hidden select stays the source of truth, so set its value and dispatch `change`, never the buttons), `shortcuts.ts` (keyboard shortcuts and the Ctrl+/ help dialog; the `SHORTCUTS` list in `main.ts` drives both), `map.ts` (the Map tab's page wiring: layer switcher, graticule toggle, legend, the site list that is also the keyboard path; it loads `globe/` only when the tab is first shown and destroys it when you leave), `globe/` (the 3D Moon in three.js, pinned `three` 0.187.0: `math.ts` is pure maths with unit tests, `tiles.ts` the Moon Trek tile quadtree, `globe.ts` the scene, controls, markers and graticule; the polar hillshade `public/map/south-pole-hillshade.jpg`, made by `make map` in `pipeline/`, is draped on a spherical cap), `summary.ts` (the planner's precomputed figures: `scripts/build-planner-summary.mjs` runs it in Node to write `public/data/planner.json`, and the planner reads that file; keep its imports with explicit `.ts` extensions), `data.ts` (lazy JSON loading, including `public/data/reviews.json`, the AI-written site reviews), `types.ts` (data contract), `sync.ts` (a shared project's WebSocket, REST calls and remembered projects), `share.ts` (the Share Project button and dialog; the collect/diff/apply code is the "shared project" block in `main.ts`; the rules and protocol are in `../_shared/shared-projects.md`), `style.css` (design tokens, dark and light). Plus `public/data/`, the published JSON from the pipeline, served at `/data/...`. Builds to `web/dist`, which the Worker serves.

**Entry points:** `index.html` → `src/main.ts`. Data types: `src/types.ts` (written in S1 from the data contract in `../_shared/stack.md`).

**Run / test:** `npm run dev` at the repo root (build + `wrangler dev`), or `npm run dev -w web` for Vite alone. `npm run check` before every commit. `npm run check:real-data` (part of `npm run deploy`) fails if any `fake-` fixture is in `public/data/`; `npm run fake-data` regenerates the three fixtures for UI work, never to be committed.

**Third page:** `how.html` (served at `/how`, entry `src/how.ts`): the solutions-architecture page, with Mermaid diagrams (the `mermaid` package loads only there). Keep its numbers (test counts, sizes) in step with reality. `learn.ts` draws the Learn view's two data charts from the loaded site file.

**Fourth page:** `qgis.html` (served at `/qgis`, entry `src/qgis.ts`): how to open Four Lights in QGIS: where to get QGIS and which version we checked, the project file to download, what is in it, the offline GeoPackage, and a table of every layer's address (built from the page's own address). The files it points at are in `public/qgis/`, written by `../pipeline/qgis-pack.sh` (not by hand), and the two pictures in `public/img/qgis-*.jpg` are QGIS's own drawings from `make qgis-verify`. Linked from the footer of every page and from the data-sources download list.

**Second page:** `sources.html` (served at `/sources`, entry `src/sources.ts`): the data-sources page, written from the `_datasets/` cards. When a card changes, change this page too. All three sub-pages are listed in `vite.config.ts`.

**Views and the guide:** `data-view` on `<html>` is `mission` or `explore` (switch in the header, `V` key, remembered per browser). Mark content with class `v-explore` (hidden in Mission) or `v-mission` (Mission only); the rules are in `style.css`. Explore is kept light: longer explanation belongs in the guide. **The guide** is `<aside id="guide">` in `index.html`, beside the tab panels in `.workspace`, switched with the Guide button at the end of the tab bar (`src/guide.ts`, `data-guide-state` on `<html>`, remembered per browser; open by default on a wide screen). A `[data-guide="<tab slug>"]` section shows only for that tab (its help and its "Try it" list); the lead paragraph and the three `<details>` (why the south pole, where AI is used, the glossary) are there on every tab. Teaching text for a tab goes in that tab's guide section and must stay factual and sourced from the same data. **Mode:** the URL's `v=` and a shared project's `view.mode` carry `mission`, `explore` or `learn`, where `learn` means Explore with the guide open (`currentMode()` / `setMode()` in `main.ts`); so a link or a followed project opens the guide too.

**Social sharing:** each page's head has Open Graph and X card tags with absolute addresses; the picture is `public/img/social-card.jpg` (1200 by 630), retaken with `node ../scripts/make-social-card.mjs <base URL>`. A new page needs the same block.

**Tests:** unit tests in `tests/` and `../api/tests/` (`npm test`, part of `npm run check`): `lights.test.ts` (the rules on known answers and on the real files), `globe.test.ts` (the globe's maths), `dom.test.ts` (chart, battery strip, icons, button groups and shortcuts against a simulated DOM), `../api/tests/worker.test.ts` (the Worker with stubbed bindings: password gate, `/api/ask`), `../api/tests/project.test.ts` (shared projects: rules, the Durable Object with fake storage, the routes). They cover the light rules, the disc, the battery, the planner sentence and summary, the AI-reply validator, and the demo scenario on the real files. Coverage: `npm run coverage` (table in the terminal, HTML in `../coverage/web/` and `../coverage/pipeline/`). End-to-end tests in `../e2e/` (`share.spec.ts` runs two browsers on one project) (`npm run test:e2e`, Playwright with the installed Chrome, about a minute and a half, **not** part of check): the demo scenario through the UI, the chart, views, theme, shortcuts, map, the question box with the model stubbed, the API, and the password gate on a second local Worker. Run them before a deploy that changes behaviour. To watch them in a browser: `npm run test:e2e:watch` (visible Chrome, slowed down) or `npm run test:e2e:ui` (Playwright's interactive window).

**The slip:** the Landing field holds the landing shown; `slipDays` in `main.ts` is how far that is from the planned landing (`slip=` in the URL, `slip` in a shared project's data). The slip buttons, `[` `]`, a planner cell on another date and the question box change both together; typing a date is a new plan (slip 0). `planner.ts` hangs its columns off the planned date, marks `th/td.planned` and `th/td.landing`, and `answerText()` adds the "Against the planned ..." sentence. A date outside the data is moved to the nearest day we have and `#plan-note` says so. The reason for the cell under the pointer or the keyboard focus is written to `#cell-why`.

**Shared state:** a new control, setting, tab or site property is either part of a shared project (`collectData`/`applyData`/`collectView`/`applyView` in `main.ts`, plus `api/src/project-state.ts`, the MCP tools and tests) or deliberately local. Follow the checklist in `../_shared/shared-projects.md`.

**Rules:** the four lights, mission window and usable days follow `../_shared/concept.md` exactly; thresholds are named constants in one file. The browser does the maths (the Worker can't: 10 ms CPU). Its own clean design (Space Apps colours not required, see `../_shared/brand.md`), 4.5:1 contrast, keyboard-usable. Phones are a design goal, not a priority: nothing should break, wide views scroll sideways. Each NASA dataset is named on screen, and anything that is our own definition or an illustrative number says so in its info tip.

**Touches:** `public/data/` is written by `pipeline/` (see `../_datasets/`). If you change the data shape, change `../_shared/stack.md`, `src/types.ts` and the pipeline together.
